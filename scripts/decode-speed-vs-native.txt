# decode-vs-native baseline — the MAXIMUM allowed (our decode time / native WIC decode time)
# for a format Windows can also decode by itself. Enforced by scripts\check-decode-speed.ps1.
#
# Anything NOT listed here uses the script's -DefaultMaxRatio (3.0). So this file is short on
# purpose: it is the list of places we are knowingly slower than Windows, and every one of them
# has to justify itself in writing. An unexplained line is the invisible trade this whole check
# exists to prevent — if you cannot write the reason, that is the answer.
#
# Ratios are only GATED where the cost is real (>=25 ms of our own time AND >=40 ms slower than
# WIC). That is why sample.ico at 7.8x is not here: it is 3.5 ms against 0.4 ms, and gating a
# 3 ms difference would produce a flaky red that gets the whole check ignored.
#
# State on 2026-08-19, over 297 samples (the 224-sample real corpus PLUS the 12 MP tier of
# test-corpus-speed, which gate A started sweeping that day): 91 have a native WIC peer, and
# exactly ONE line remains below. The DDS family briefly earned a second — it only became
# visible at all once a 12 MP sample existed to measure — and then lost it again the same day
# when the cost was fixed rather than excused (see the note under this paragraph). Most are far
# FASTER: camera RAW by 50-100x, because we read the embedded preview instead of demosaicing,
# and after 2026-08-19's work JPEG runs ~0.22x, BMP ~0.46x, GIF ~0.82x, DDS ~1.56x and PNG at
# 12 MP ~0.99x.
#
# Earlier state, kept because it dates the entries: on 2026-08-18 the real corpus alone showed
# 75 peers and exactly ONE slower format (WebP was the second, fixed that day — WebP now routes
# through the OS codec when installed, ~103 ms -> ~22 ms, with the pure-Rust tier as the
# unchanged fallback).

# dds / dxt1 / dxt5 CARRIED A LINE HERE ON 2026-08-19 AND NO LONGER DO, which is the outcome
# this file is supposed to produce rather than accumulate. They were 3.2-4.6x native at 12 MP
# and were about to be excused at 5.0 with a written reason. Instead the reason got fixed: a
# BC1/BC2/BC3 block whose MEAN is all the caller wants is now computed from its two endpoints
# and a 4-bin index histogram, never expanding sixteen texels (decode/dds.rs block_mean_fast).
# Measured 4x on that step, 65 ms -> 16 ms, and end to end 90 ms -> 33 ms, so 3.59x -> 1.56x -
# inside the 3.0 default with no line at all. Byte-identical to the full decode, proven over
# 60k blocks per format plus the endpoint-ordering and alpha-mode boundaries.
#
# The lesson, because it nearly went the other way: the FIRST version of that fast path
# measured 3x SLOWER than simply expanding the block, and the gate showed no change at all.
# Both readings were true and neither meant what it looked like - the micro-benchmark was
# comparing against the bare expansion instead of against expand-then-average, and the naive
# accumulate-per-texel loop really was slow until it became a histogram. Measure against the
# thing you are actually replacing.

               # subprocess - and that is now the whole allowance. As of 2026-08-19 every
               # TAGGED 8-bit colour case (explicit BT.601 matrix 5/6, avifenc's default, and
               # "unspecified" matrix 2, plain ffmpeg's default) decodes through the OS AV1
               # decoder's raw NV12 with our own BT.601 matrix (decode/avifmf.rs): measured
               # worst channel error 1-2 against the pre-encode truth, ~8 ms on ordinary sizes
               # and ~98 ms on a 6 MP file, against ~390-1261 ms via the subprocess it replaced.
               # High-bit-depth AVIF rides WIC + the inverse transfer curve (2026-08-18), and
               # 8-bit BT.709 always rode plain WIC.

               # The remaining magick case is a file whose container carries no colr box AND

               # header: guessing would risk exactly the wrong-colour bug this whole chain
